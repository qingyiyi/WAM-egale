## 2. 项目理解的起点

我们的目标是加速冻结 LingBot-VA/WAM 的连续动作去噪推理，并在机器人闭环任务中控制成功率损失和轨迹长度变化。

待验证的研究主线是：
投机产生候选去噪状态 → 将细粒度串行 target 工作重组为多候选 verifier → 利用共享权重、合法共享条件/历史和候选维度组织计算 → 在质量约束下降低有效推进成本及任务成本。

这是待验证的因果链，不是已经成立的论文贡献。算法侧和系统侧已有各自实测，但单层算子尚不能自动继承或改善完整机器人任务结果。不能把旧投机倍数、reset 倍数和新单层倍数直接相乘。

目前两条工作线：

1. 投机：Transformer draft、教师监督、候选树、连续误差接受、prefix 选择、bonus/fallback，以及可选 PF2；比较成功率、轨迹长度、接受行为与真实成本。
2. 单层系统：将完整 Transformer block 组织为一个 persistent kernel，在内部对投影、self/cross attention、norm、RoPE、FFN 和残差分块；研究 warp 分工、TMA 与局部流水。范围是一个完整 block，不是把 30 层合成一个 kernel。

MegaTransformer 是研究称呼，具体机制以已采用源码为准。不要将普通 batch、现成缓存或尚未采用的 DSM/完整 DAG 设计包装成已经实现的新贡献。

## 3. 阅读方法时必须弄清的实现

先沿实际导入链和部署 manifest 查清，不依据类名或历史聊天猜实现：

- target 的动作/视频分支、动作 latent 与隐藏维度、scheduler 和 CFG，以及哪些部分真正被投机。
- draft 的输入、输出、参数量、层数、attention 形式、normalizer、dtype；训练的教师标签、loss、数据生成模型、FIT/CAL/DEV 来源及 checkpoint 选择。
- draft 如何递归生成候选，teacher 如何验证，误差如何计算，合法路径怎样选，拒绝、bonus 和终端步骤怎样推进 scheduler。
- 历史 KV、条件 KV、候选私有状态的共享范围及更新时机。不要把候选私有 KV 当共享 KV。
- persistent block 的阶段、tile 形状和数量、每阶段 warp 分工、Tensor Core/CUDA Core 工作、shared/register/global 数据流、屏障与就绪条件。
- 源码中的实际采用版本与试验版本：成功编译或有限精度通过，不代表已采用或比 baseline 快。

可用于定位的已知接口事实，仍须按当前版本核验：

- Long 历史 TF64 是小型单层 Transformer，约 5.3 万参数；其他环境输入维度/参数量可能不同，不把 Long 配置泛化为所有套件。
- K2/B2 树曾打包 7 个候选状态，CFG 两路，外部 verifier batch 为 B14；每候选 action Q16。7 候选不等于一个可互相注意的 Q112 序列。
- 对线性层可讨论合并行数，但实际 GEMM 的 M/N/K 必须来自真实调用。action latent 的 112 维不是 Transformer hidden size。
- 历史接受分数为 abs(delta_sigma) * L2(v_draft - v_target)，模型方向 BF16、打分 FP32；原 tau 是经验校准值，不是轨迹或成功率保证。新的套件阈值候选与旧阈值分版本。
- PF2 是 S、S、T 循环：两个完整 speculative policy chunk 后执行一个完整 canonical target chunk。bonus 是投机轮内额外推进，二者不同；PF2 也不会恢复已偏离的机器人物理状态。
- 所有比较臂统一使用已验证的 full512 BF16 reset bank；冷启动、bank 构建和 warm 运行分列。
- RTX 5090/SM120 的当前实现能力、指令和存储约束以真实源码/编译记录为准，不把 SM100、Hopper 或 MegaMoE 的硬件特性直接套过来。

具体数字或公式只有核验到出处后才能进入正文；不完整信息写成明确占位或列入缺口。

## 7. 数据与结论的边界

- 以完整 episode/初态组区分 FIT、CAL、DEV 和 TEST；随机拆 query 行不构成独立任务测试。暴露过的面板、用于选型的 case 和新命名空间不能重新命名为独立 holdout。
- 三个小 LIBERO 套件、Long、LIBERO-90、LIBERO-100 是不同范围；查清实际 suite/task/init/seed/N，不按目录中的“100”猜任务数。LIBERO 与 RoboTwin 的训练、checkpoint、动作维度和终止协议分别核对。
- 接受率、target forward 数、合法提交深度、成功率和轨迹长度是不同指标。离散 token 投机的严格分布保持结论不能直接搬到连续动作近似接受。
- 当前四项标志在已有证据中均为 false：engineering_quality_screen、independent_test_complete、noninferiority_established、formal_performance_permission。只有新的可追溯正式记录才能改变；写作助手不能自行放行。
- 失败、慢成功、超时/PARTIAL 和初态无效分别报告。成功子集的长度/耗时是补充分析；不能删掉失败或长尾后宣称总体保持质量或加速。
- 轨迹长度要注明是环境 timestep、实际命令数、policy chunk 数还是内部去噪更新数。失败罚分按各环境的预登记协议，不能把某套件的 800 套到所有环境；实际执行步数与罚分分列。
- 成功率报告 N、逐任务/配对胜负与区间；不显著不代表非劣，三条风险成功或 CAL 接受提高不能替代独立闭环质量。
- 本机当前阈值比较以成功率、轨迹长度、接受深度和失败为主，耗时为附带成本，不把它描述成已完成的独占正式 benchmark。

## 8. 性能与系统主张

主机制量优先使用：

    C_update = sum(T_round) / sum(g)
    T_round = T_draft + T_pack + T_verify + T_accept_commit + T_extra_target

g 是实际合法提交的 scheduler 更新数，包括真正执行的 bonus/fallback，不重复计数；不是候选数、环境动作数或任务成功数。另报完整 policy chunk 成本、chunks/s、自然 episode 成本、cold/warm E2E、包含失败成本的成功吞吐，严格说明各边界。

kernel、block、30层 verifier、完整 chunk 与机器人 episode 是不同层级。单层重放收益、减少调用、逻辑读取减少都不能直接等同于 E2E 收益或实测 HBM 减少。阶段插桩与无插桩整层分列，不能把有重叠的阶段相加或把各段加速比相乘。

对照包括原 Torch、已有 guarded/shared-prefix 与自有路径；guarded 是项目路径，不是 Torch 官方实现。双方同硬件、dtype、缓存、输入与 eager/Graph 条件，已经存在的缓存/批处理收益不重复计算为新增贡献。shared memory 容量、静态 local memory、理论 FLOPs/byte 不冒充实际动态流量或 stall 原因。

如果写“算法系统协同”，先核对具体实验中 A/S 两个符号各代表什么，并检查是否有完整的四格对照和交互证据。历史文档曾用相同符号指不同因素，不能混写。

当前局部方法探索中的 DSM/cluster、成对K分段、就绪DAG等负结果要按版本留存。把“可运行”“有限精度通过”“候选改进”和“当前采用”分开。不能因某个 DSM 版本慢，就断言硬件不支持 DSM 或该机制普遍无效。
