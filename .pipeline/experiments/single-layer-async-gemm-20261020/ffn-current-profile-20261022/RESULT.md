# 当前B版本FFN瓶颈：真实时间线＋Nsight Compute

OBSERVED：当前生产研究源码/DSO未改。远端A100-SXM4 GPU0，对三档真实B14输入分别完成两进程、72整层＋72独立FFN时间线；本机自然空闲窗口采同一B版本独立FFN的NCU。有限输出、输入/有效KV/RNG通过，资源相同。四科学权限与production_admitted仍false。

## 主要判断

当前剩余差距优先指向**FFN1最后一组生产得晚，以及自有整层执行的额外指令/局部内存开销**。不是FFN2等待第一段结果占了很长时间，也不能把NCU的barrier stall百分比当可删除墙钟时间。

此前选定源码无插桩独立FFN相对原Torch仍慢8.912%/9.084%/9.154%（短/中/长），这轮诊断副本复现约9%–10%的差距。诊断副本不是新的生产版本，不能把副本计时差异说成生产退化。

时间线以FFN流水函数体内首个时间戳为零点：函数入口之前的ABI保存、return时的恢复不在这张分段表内；独立FFN总计时与NCU包含它们。

各项是两进程各12条trace中位数再汇总；任务相互重叠，不将表中各行相加成整层时间。globaltimer约1.024μs量化，小于该粒度的等待不能精确分解；最后消费者的等待约1μs不代表所有任务等待相同。

原Torch独立FFN1＋GELU约179–180μs、FFN2＋残差约139–142μs。自有FFN1生产完成208–209μs与Torch FFN1+GELU是相近的工作边界，但自有生产阶段同时有FFN2在运行；该对照用于定位完成得晚，**不是隔离FFN1的正式加速比**。独立计时的Torch分段也不相加代替整体实测。

## 为什么FFN1仍有长尾

源码whole_layer.cu:315/361/427：108个常驻CTA先各做一个M128×N256生产tile。前108个之后，CTA0–11各再做一个M32×N256尾部tile；每个仍完整归约K3072。三个较早的组约125–130μs就绪；第四组必须等待这12个尾部任务，约207–209μs才全部就绪，之后才能派该组24个FFN2任务。

代表真实trace：尾部12个tile约126–128μs开始，MMA主循环约68–72μs、写回/GELU约6–8μs，约207μs结束。M从128减到32不等于时间变为四分之一：K循环仍96次；每个tile仍读取相同N×K范围的权重，且4个大尾块拆成12块，逻辑权重读取有重叠。实际L2/HBM复用还要按硬件计数解释，不能把逻辑重复读取直接写成HBM三倍。

最后一组就绪后，FFN2确实在计算：约92μs矩阵乘分段，约18μs写回＋残差。上一个版本约32μs的旧写回结果已不代表当前版本；本次四元素写回后的实测约18μs。

108CTA并非108个SM一直有有效计算。时间线推得平均约73个CTA处于计算/写回区间；这是软件活动区间统计，不是NCU的SM利用率。

local指地址空间，不等于全部请求都落到HBM；多出的54MB DRAM不能全部归给local。单次NCU未锁时钟/清缓存，保留原缓存条件；这是同机机制采样，不能与远端时间相除或当正式延迟。此前R2的55.7MB local总请求是另一版本历史值，不把下降单独归因生产函数内联。

自有：255寄存器/线程、约101.12KB/CTA（含运行时开销）、108CTA×256线程、约12.50%活动warp占用。原Torch FFN1也是112CTA×256线程且约12.49%占用；FFN2为96CTA×128线程，约6.23%。因此“occupancy低”或“CTA数量少”单独不能解释性能差距。

自有整个混合FFN Tensor Core active约41.99%，Torch两个纯GEMM约77.57%/81.29%；边界不同，不能称自有MMA吞吐只有一半。自有barrier stall约42.48%是活跃warp的发射停顿比例，包含CTA内部等待/退出等待，不是42.48%的整层墙钟。时间线中最后提交后的收尾仅约6μs；很多较早完成的CTA在等待最后一组计算结束，删除屏障并不能让最后一组凭空完成。

## local流量进一步定位：当前DSO的函数边界

再次读取当前选定B二进制对应SASS，而非旧R2：`action_ffn_pipeline`仍是noinline设备函数。其257条静态LDL/STL中，126条出现在第一条HMMA之前，128条在最后一条HMMA之后，仅3条位于整个HMMA区间之间（还包含两阶段间的调度）。编译器记录该函数520字节stack frame、512字节spill stores/loads。

入口126条标量STL若由108×256线程各执行一次，写入payload约13.93MB；与NCU实测每方向14.7/15.1MB的量级相吻合。**当前动态local主要来自函数入口/出口的寄存器保存恢复是强支持的解释**；不能因此把全部DRAM增量等同ABI，也未做删除该边界的因果计时对照。更不能仅凭static local=920B就宣布MMA主循环每次迭代都在溢出。

当前只内联了FFN1生产函数，外层FFN流水函数仍保留调用边界，这说明为何local流量已经下降但没有归零。源码whole_layer.cu:427，静态归档见CURRENT-SASS-LOCAL-PLACEMENT.json。
