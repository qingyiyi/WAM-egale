# FFN1尾部行块分摊：有限实测有效，尚未解决全部FFN差距

## OBSERVED

用户确认先FFN1尾部分摊，再处理FFN2写回和函数保存恢复。本轮直接改optimized，仅尝试一个方案；baseline、投机代码及保护文件未改。

原FFN1有112个M128×N256生产tile（第二行块96行有效），108个常驻CTA中的4个需要再算一块。这4块均属于最后组3。现保留前108块，将末4块每块拆成3个M32×N256任务，由CTA0–11分担第二轮。总生产任务120，完成计数28/28/28/36；FFN2仍96个分段任务。K3072、K32迭代、bias、BF16舍入、GELU及FFN2两段7168的提交顺序不变。

以上是远端A100-SXM4 GPU0无其他compute app时的单层warm CUDA Graph；双方预计算最终Cross K/V，原Torch使用静态合法slot适配。不是完整WAM、chunk或机器人E2E。原Torch是性能对照；R2只用于定位本次改动的增量，不是另一外部baseline。

两独立进程，三真实输入，150轮每臂预热、24轮交错、每事件10次replay；每进程每档均改善，范围1.723%–2.113%。计时与精度fixture路径逐项一致（6/6）。9真实签名和36结构控制，共225次有限核验，23个共同中间量、最终输出、有效KV、输入及RNG通过逐位/状态要求；正常路径与debug也一致。不是所有输入的数值证明，也不是闭环质量证书。

## 机制与代价

debug观测每版本72条：最后生产组仍为组3。以本次最早组就绪为相对起点，最后组就绪间隔从约118–119us缩短至89–90us；最后消费完成间隔约246us→224–225us。该观察支持尾部分摊缩短关键链，但不是正常计时，也不是从统一绝对FFN入口测到的FFN总耗时。

最后生产到最后消费的尾段反而约127us→134–136us，故输入提前并未全部转成收益。两版仍108CTA、256线程、100096B shared、255寄存器；静态localSizeBytes1144→1224。新tail设备函数编译器报告72B stack、64B spill store/load；这是编译属性，不是动态HBM字节或确定耗时。新增任务重复读取部分权重，并增加一次设备函数/发布开销。本轮未采动态NCU计数，不能定量归因尾段增加的原因。

## HYPOTHESIS / UNKNOWN

更快完成**最后所需整组输入**可以改善性能；更早算完第一行块或某个通道tile，不保证最终输出更早完成。FFN2每行依赖全部14336个中间值，目前允许两个7168半段各自就绪后执行，但最终输出仍需两段。

当前仍有FFN2计算、门控残差写回和设备函数保存恢复开销。上一轮独立FFN比原Torch慢23.4%–23.8%是旧R2结果；本轮没有重新测独立FFN，不能把整层减少量直接从旧差距中相减、宣称FFN已经对齐。本轮也没有新L2/DRAM/occupancy数值或B2性能结果。

## RECOMMENDATION

两机研究入口采用这一个有限通过的新版本，原R2源码与二进制保留。下一步先单因素处理FFN2最终写回/索引，再处理函数保存恢复；不继续无限细分生产tile，也不以提交等待作为第一目标。四项科学权限和production_admitted仍false。
